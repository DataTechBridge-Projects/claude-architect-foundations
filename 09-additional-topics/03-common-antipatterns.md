# Common Antipatterns
{: .no_toc }

*Video duration: 21:25*

Every antipattern in this lecture shares two properties: it's tempting, for a specific and usually reasonable-sounding reason, and it fails in a way that's predictable once you know the layer's underlying trade-offs. That combination is exactly what makes antipatterns worth cataloging deliberately rather than trusting yourself to avoid by instinct — the temptation is real, it doesn't announce itself as a mistake, and the exam is built to describe these situations from the tempted architect's point of view and ask whether you'd fall for it too. What follows is organized by layer, three or four per layer, closing with one meta-antipattern that operates above all five.

## Agentic Layer Antipatterns

**Over-agentifying a deterministic task.** A task whose correct behavior can be fully specified in advance — validate this schema, run this test suite, extract these five fields from a standard form — gets handed to an autonomous agent with broad judgment anyway. It's tempting because "agent" sounds more capable and more future-proof than "fixed script," and because building an agent once feels like it covers every future variation without more engineering. It fails because autonomy adds real cost — more tokens, more latency, more unpredictable paths — for a task that gets none of autonomy's benefit, since there was no genuine ambiguity to resolve in the first place. Worse, it makes the system harder to audit: a fixed workflow's behavior is provable in advance, while an agent's is only observable after the fact, and you've traded that provability away for nothing.

**Multi-agent coordination for its own sake.** A single agent's responsibility gets split across a coordinator and several subagents without a genuine need for specialization, parallelism, or context isolation driving the split. It's tempting because a multi-agent diagram looks more sophisticated and more "enterprise-grade" in a proposal, and because decomposing a hard problem into named pieces feels like progress even when the pieces don't need to run independently. It fails because coordination is never free: context has to be split and reconciled across agents, a failure in one subagent can cascade into the orchestrator's reasoning or get silently lost in a report-back, and the resulting system is materially harder to debug and observe than one well-scoped agent would have been — for a problem that a single agent could have solved with less machinery and less cost.

**A loop with no real stopping condition.** An agent is given an open-ended goal and turned loose without a concrete, reachable definition of "done" beyond "produce a final answer eventually." It's tempting because defining explicit stopping conditions feels like unnecessary upfront work when the agent will "just figure out" when it's finished. It fails because a loop with no legitimate exit condition manufactures one: it keeps calling tools past the point of diminishing returns, drifts from the original task as intermediate results accumulate in context, or produces a confident final answer that's really just what was left standing when a turn limit finally hit. The fix isn't reducing autonomy — it's defining, explicitly, what a legitimate stop looks like before the agent is allowed to run.

## Tool Layer Antipatterns

**Tool sprawl.** New tools get added for every new capability, one at a time, without periodically asking whether an existing tool could have covered the case with a different argument. It's tempting because adding one narrow tool feels safer and more incremental than modifying an existing one's contract, and each individual addition looks harmless in isolation. It fails because the disambiguation burden a model faces at selection time grows with every near-duplicate tool added to the set — descriptions that were perfectly clear against three alternatives become genuinely ambiguous against fifteen, and wrong-tool selection rates climb in a way that's invisible until you measure it directly.

**Raw stack traces standing in for designed error responses.** A tool's failure path just passes through whatever exception the underlying system threw, rather than translating it into a message built for a reasoning caller. It's tempting because it's zero additional engineering effort — the exception already exists, so surfacing it looks like reuse rather than extra work. It fails because a stack trace was optimized for a human reading source code, not a model deciding what to do next: it doesn't say whether the failure is retryable, it leaks implementation detail that means nothing to the model, and it frequently causes the model to either retry blindly against a permanent failure or hallucinate a workaround because it was never told what actually went wrong.

**Schema validity mistaken for operational safety.** A tool gets a tightly typed, well-validated input schema, and the team treats that as if it were a safety boundary on the underlying action. It's tempting because schema work is visible, testable, and satisfying to complete, and it's easy to conflate "this call is well-formed" with "this call is safe to allow." It fails because a schema only enforces shape — it says nothing about whether the action itself should be permitted. A narrow, perfectly valid schema wrapped around a broad-capability action (the canonical case being a shell-execution tool with a one-parameter schema and effectively unlimited real-world reach) still needs safety enforced through permissions, sandboxing, and scoping around the tool, not through the schema, and teams that stop at schema validation have built a locked-looking door with no wall around it.

## Workflow Layer Antipatterns

**Ad hoc Claude usage instead of CI/CD integration.** Engineers invoke Claude manually and inconsistently for tasks like code review or documentation updates, rather than wiring those tasks into the pipeline as a defined, triggered step. It's tempting because it's faster to get started — no pipeline configuration, no defined trigger, just a person running a prompt when they remember to. It fails because ad hoc usage is invisible to the rest of the team, produces non-reproducible results since the same "step" behaves differently depending on who ran it and how, and has no natural place for gating, logging, or rollback — exactly the operational rigor every other step in a delivery pipeline already has.

**Treating `CLAUDE.md` as the answer to every knowledge problem.** Large, dynamic, or highly query-specific information gets stuffed into `CLAUDE.md` because it's the familiar, easy lever to reach for once a team has adopted it. It's tempting because editing a file everyone already knows about feels lower-friction than standing up a retrieval pipeline, and the payoff (the agent "knows" the thing) is immediate. It fails because `CLAUDE.md` content loads on every single session regardless of relevance to the task at hand — a large or fast-changing knowledge base crammed into it bloats every session's context with material that's irrelevant most of the time, goes stale the moment the underlying knowledge changes, and should have been retrieved on demand instead of paid for upfront on every turn.

**A single centralized convention forced onto every team.** One organization-wide template for gate depth, review process, or tool access gets mandated uniformly, regardless of what any individual team's workflow actually needs. It's tempting because centralization looks like governance and consistency, and it's genuinely easier to communicate and audit one rule than many. It fails because a real fraction of workflow decisions are legitimately local — report formats, how deep a review needs to go, which Skills a team maintains — and forcing them into one shape either strips out configuration a team genuinely needed or piles on process a team's actual risk profile didn't call for, producing friction without producing the safety the centralization was meant to buy.

## Prompt Layer Antipatterns

**The prompt as the only safeguard.** A downstream system needs guaranteed, parseable structure, and the entire enforcement strategy is a well-worded request — "please respond with valid JSON only" — rather than a schema-constrained or tool-call-based mechanism. It's tempting because it's the cheapest possible fix: no schema to design, no validation code to write, just better wording. It fails because a request is not enforcement; the model can and occasionally will drift from a polite instruction under the right pressure, and "occasionally" is exactly the failure rate a production system parsing that output can't tolerate.

**Grading your own homework.** Output quality is checked by asking the same model, in the same pass, to critique its own draft, and that self-critique is treated as sufficient review. It's tempting because it's cheap — one additional instruction in the same prompt, no separate call, no separate criteria — and it often produces output that reads as more polished. It fails because a model checking its own work in the same context inherits the exact blind spots that produced any error in the first place; genuinely independent review needs a separate pass with separate criteria and limited visibility into the generator's own reasoning to have a real chance of catching what the generator couldn't see in itself.

**Example sets that teach the wrong lesson.** Few-shot examples are assembled from whatever cases happened to be on hand, clustering around the typical case or accidentally sharing some incidental detail unrelated to the actual pattern being taught. It's tempting because pulling a handful of recent, representative-looking examples is fast and they individually look correct. It fails in two distinct ways: an example set clustered around the center teaches the model that the narrow, typical cluster is the whole pattern and leaves it unprepared for edge cases; and an example set with a shared incidental correlation (every "urgent" example happens to mention money) teaches the model that correlation as if it were the actual rule, producing confidently wrong classifications the moment the correlation doesn't hold.

## Context Layer Antipatterns

**Context window bloat from "just in case" loading.** Documents, history, and retrieved material get pulled into context on the theory that more available information can only help. It's tempting because deciding what to leave out feels risky — what if the thing you excluded turns out to matter? — while including everything feels like the safe default. It fails because irrelevant context isn't neutral: it crowds out the material that's actually load-bearing for the current step, makes it harder for the model to identify which instruction or fact among several plausible ones actually applies, and degrades instruction-following in ways that are hard to trace back to "too much context" after the fact.

**No provenance tracking.** Every fact present in context is treated as equally trustworthy, with no metadata about where it came from, how current it is, or how it should be weighed against a conflicting fact elsewhere in the same context. It's tempting because provenance metadata feels like extra plumbing on top of a system that already technically works. It fails the moment two sources disagree, or a filtered, narrowed, or stale result gets treated as if it were exhaustive ground truth — the system has no way to recognize the ambiguity because nothing marked the fact as uncertain in the first place, and a genuinely risky situation ends up looking, from the model's point of view, exactly like a clean, single-answer case.

**Assuming a human review gate exists without building one.** An irreversible or high-stakes action path gets designed on the implicit assumption that "someone will catch it if it's wrong," without an actual checkpoint where a specific human is positioned, informed, and empowered to intervene before the action happens. It's tempting because it's genuinely easier not to design the gate explicitly — the system "feels" safer just because a human is somewhere in the general vicinity of the process. It fails because a safety net that was never actually built catches nothing; by the time anyone notices the gap, the irreversible action has already happened, and the postmortem finds a design that assumed a safeguard rather than one that implemented it.

**Guess-and-continue as the silent default.** When context doesn't contain enough information to proceed safely, the agent picks the most plausible interpretation on its own and keeps going, rather than flagging the assumption, asking, or escalating. It's tempting because it keeps the task moving and produces an answer instead of a pause, which looks efficient in the moment and in a demo. It fails because a silently resolved ambiguity doesn't announce itself — the wrong assumption gets built on top of by every subsequent step that trusts it, and the resulting error is far harder to catch from the final output than a single visible wrong answer would have been, because everything downstream of it looks locally reasonable.

## The Meta-Antipattern: Optimizing One Layer While Ignoring the Seams

Every antipattern above is a single-layer mistake, but the most expensive antipattern in real architectural work operates across all five at once: a team invests real engineering effort perfecting one layer — an elegant tool schema, a beautifully tuned prompt, a carefully tiered context-retrieval pipeline — while leaving the other four layers as unexamined defaults. It's tempting because deep, visible expertise in one layer is satisfying to build and easy to demonstrate, and because a team's skills are rarely evenly distributed across all five domains. It fails because the five layers interact, and a system's actual reliability is bounded by its weakest layer, not its strongest one — a beautifully designed tool set connected to an agent with no stopping condition, or a rigorously versioned prompt fed by a context window nobody curates, fails for reasons that have nothing to do with the layer the team was proud of. The discipline this course has been building toward is the antidote: treat all five layers as one system to be reasoned about together, because that's how they actually fail together in production, and it's how the CCA-F's hardest scenario questions are built to be answered.

**Why it matters for the exam:** A large share of CCA-F scenario questions are, structurally, "here's a system that looks fine — what's the antipattern hiding in it?" Working through this catalog by layer, and being able to name the specific tempting-but-wrong reasoning behind each one, is more exam-relevant than memorizing the fixes in isolation, because the exam almost always describes the temptation before it describes the failure.
