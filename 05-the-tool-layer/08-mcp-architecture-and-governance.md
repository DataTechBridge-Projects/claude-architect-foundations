# MCP Architecture & Governance
{: .no_toc }

*Video duration: 19:10*

Every tool discussed so far in this module has been treated as if it simply exists — defined, described, schema'd, ready to be called. This lecture is about the layer beneath that assumption: how a tool actually gets exposed to Claude in the first place, at scale, across an organization with many systems and many teams, without every integration being a bespoke, one-off piece of glue code. That's the problem the **Model Context Protocol (MCP)** exists to solve, and it's also where tool design stops being purely a per-tool craft question and becomes an organizational governance question.

## The problem MCP solves

Before a standard existed, connecting an LLM to an external system — a database, a ticketing tool, an internal API — meant writing custom integration code specific to both that system and that particular LLM application. If your organization wanted Claude to access Jira, Salesforce, and an internal inventory database, you'd write three separate, non-reusable integrations, each hand-rolling its own tool definitions, its own authentication handling, and its own error translation. If a second team, building a different Claude-based application, also needed Jira access, they'd write a fourth integration from scratch, duplicating work that had already been done once.

**MCP (Model Context Protocol)** is a standard, open protocol for exposing tools, data resources, and prompts to an LLM client in a consistent, reusable way. Rather than every integration being bespoke, an MCP server is written once, against the protocol, and any MCP-compatible client — Claude Code, Claude Desktop, or a custom application built on the Claude API — can connect to it and gain access to whatever tools and resources it exposes, without the client needing integration-specific code for that particular system. The protocol standardizes the *shape* of the interaction (how tools are listed, how they're invoked, how results and errors come back, how resources are read) the same way structured tool use itself standardizes the shape of a single tool call — it's the same underlying idea, generalized from "one tool, one schema" to "an entire connectable capability surface, one protocol."

## MCP architecture: servers, clients, and the connection between them

MCP's architecture has two sides, and understanding the division of responsibility between them is the core of this section.

An **MCP server** is the piece that knows about a specific external system — Jira, a filesystem, a database, an internal company API — and exposes some combination of three things through the protocol: **tools** (invokable actions, structured exactly like the tool definitions covered earlier in this module — name, description, input schema), **resources** (readable data the model can pull into context, like a file's contents or a database record, without necessarily invoking an action), and **prompts** (reusable prompt templates the server can offer to a client, though this is used less commonly in practice than tools and resources). The server is responsible for translating between the protocol's standard shape and whatever the underlying system actually requires — its own authentication scheme, its own API quirks, its own error formats — so that everything the client sees on the other side of that translation looks like a normal, well-formed MCP tool or resource, regardless of how idiosyncratic the underlying system is.

An **MCP client** is the piece embedded in the LLM application — Claude Code has one built in, and any application built on the Claude Agent SDK or directly on the Claude API can implement one — that connects to one or more MCP servers, discovers what tools and resources each one exposes, and makes those available to the model as part of its normal tool-use flow. From the model's perspective, a tool exposed through an MCP server looks exactly like any other tool: a name, a description, a schema, invoked the same structured way covered throughout this module. MCP is fundamentally a *plumbing* standard — it changes how a tool gets connected to an application, not how the model perceives or calls it once connected. Everything from the earlier lectures in this module — naming discipline, description quality, schema design, honest error responses — applies with exactly the same force to a tool exposed through MCP as to one defined directly in application code, because the model can't tell the difference and shouldn't need to.

The connection between a client and a server can run locally (a server running as a subprocess on the same machine, communicating over standard input/output — common for local tools like filesystem access) or remotely (a server running elsewhere, reached over a network transport). This flexibility is part of what makes MCP useful at organizational scale: a company can run one centrally-hosted MCP server exposing, say, its internal customer database, and every Claude-based application across the organization that needs that data connects to the same server rather than each reimplementing that access independently.

## Why this matters architecturally: reusability and the ecosystem effect

The practical payoff of this architecture is reusability in both directions. A single MCP server, once written, can be used by any number of clients — Claude Code sessions, custom internal applications, other AI-assisted tools — without being rewritten for each. And a single client (Claude Code, or any application with an MCP client built in) can connect to any number of servers, mixing capabilities from different systems and even different vendors into one coherent tool set available to the model in a given session, without the client needing bespoke code for each one.

This is also why an ecosystem of MCP servers has grown quickly since the protocol's introduction — servers exist for common developer tools, popular SaaS products, databases, and countless internal systems, maintained by Anthropic, by the vendors of the underlying systems themselves, and by the open-source community. That ecosystem effect is genuinely valuable: instead of every organization independently building a Slack integration or a GitHub integration for their Claude-based agents, most reach for an existing, community- or vendor-maintained MCP server and configure it, the same way most software teams don't write their own HTTP client library from scratch. But that same ecosystem effect is precisely what turns MCP from a pure engineering convenience into a governance problem, which is the second half of this lecture.

## The governance problem: a growing, heterogeneous tool surface

Once it's easy to connect Claude to a new capability by pointing a client at a new MCP server, the natural organizational trajectory is for that surface to grow quickly — a team adds a server for their ticketing system, another adds one for a cloud provider's API, another connects an internal database, and within a fairly short time an organization can have a sprawling set of MCP servers connected across various Claude-based applications, of wildly varying quality, trustworthiness, and blast radius. This growth is exactly the kind of situation that demands the same governance discipline any organization applies to third-party code dependencies or third-party API integrations — because that's structurally what an MCP server is: a piece of code you didn't necessarily write, running with some level of access to real systems, that you're now giving a language model the ability to invoke.

Several governance questions become unavoidable once a tool ecosystem reaches this scale, and the CCA-F treats reasoning through them as a core architectural skill rather than a niche operational detail.

**Which servers are trusted, and by what process?** Not every MCP server available in the broader ecosystem should be connectable by default within an organization. A server maintained by Anthropic or by the vendor of the system it wraps carries a different trust profile than a community-maintained server of unknown provenance, and a server pulled from an unfamiliar source carries a real risk that its tool descriptions, its error handling, or its underlying implementation don't meet the bar the rest of this module has been building toward — or, more seriously, that the server's code does something other than what it claims to do with the credentials it's handed. A mature organization typically maintains an approved list of vetted MCP servers, with some review process (security review, code review, or at minimum a vendor-trust assessment) gating what gets added to it, rather than leaving "should we connect to this server" as an ad hoc decision made independently by whichever team happens to want the capability that week.

**What scope of access does a connected server actually get?** Connecting an MCP server to a Claude Code session or application doesn't have to mean granting it unlimited access to whatever underlying system it wraps. The same least-privilege principle that governs API keys and service accounts in traditional infrastructure applies directly here: a GitHub MCP server used for an agent that only needs to read issues shouldn't be configured with a credential that also grants write access to production branches, even if the server technically supports write operations. Scoping access at the credential level — not just hoping the model chooses not to use tools it technically has access to — is the concrete mechanism for enforcing this, and it's a direct extension of the workflow-safeguarding principle from the Agentic Layer: high-blast-radius capability should be structurally unavailable where it isn't needed, not merely discouraged through a prompt instruction the model might not follow under all circumstances.

**Who decides which servers a given session or application can connect to?** In an organizational setting, this is rarely left to individual discretion at the point of use. Centralized configuration — an approved server list, standard credential-scoping templates, policy about what kinds of servers require additional review before connection — is the pattern that scales, versus every engineer independently deciding what to connect to their own Claude Code session with whatever credentials they happen to have on hand. This mirrors, again, a pattern familiar from traditional software supply-chain governance: most organizations don't let individual engineers freely install arbitrary third-party packages into production systems without some review process, and the same discipline increasingly applies to MCP servers, because functionally, a connected MCP server *is* a dependency with real system access.

**What's the audit story?** Because MCP servers can expose tools with real side effects — writing to a database, sending a message, modifying a ticket — the infrastructure-level concerns from the earlier aside on tool-usage infrastructure (logging, auditability) apply with particular force here, since a growing set of connected servers, each with their own tools, multiplies the number of places a consequential action could originate from. Being able to answer "what actions did this agent take, through which server, with what credential, and why" after the fact is not optional at any meaningful scale — it's the difference between a governable tool ecosystem and one where a security or correctness incident is effectively unforensicable.

## Security implications of a growing tool ecosystem

Beyond the governance process itself, it's worth naming the specific security shape of the risk MCP introduces, because the CCA-F treats this as a live architectural concern rather than a hypothetical. A connected MCP server is, functionally, code with access to real systems that a language model can be induced to invoke — and that access is only as trustworthy as the server's own implementation and the scope of credential it's been handed. A malicious or compromised MCP server could, in principle, expose a tool whose description looks entirely reasonable while its underlying implementation does something the description doesn't disclose — exfiltrating data passed to it as an argument, for instance, or taking an action beyond what its stated purpose implies. Because the model has no way to inspect a server's actual implementation and can only act on the tool's declared name, description, and schema — exactly the surface this whole module has been about — the burden of verifying a server's trustworthiness sits entirely with the humans deciding whether to connect it, not with the model deciding whether to call it.

This is also why prompt-injection-adjacent risks compound with a growing tool surface: a tool result returned from a connected server — a document's contents, a search result, a webpage fetched through a resource — is itself untrusted input from the model's perspective the moment it enters context, and a poorly governed server is one additional vector through which adversarial content could reach the model disguised as an ordinary tool result. Scoping credentials tightly, vetting servers before they're connected, and treating tool results as data rather than instructions are complementary defenses, not substitutes for one another, and a mature MCP governance posture applies all three rather than relying on any single one.

**Why it matters for the exam:** Expect questions that ask you to distinguish an MCP server's responsibilities from an MCP client's, to identify what MCP standardizes (the connection and discovery protocol) versus what it doesn't change (tool design principles, which apply identically to MCP-exposed tools), and scenario questions where an organization's MCP server sprawl is described and you're asked to identify the missing governance control — typically credential scoping, a server vetting process, or an audit mechanism. The exam is less interested in MCP's wire-level details than in your ability to reason about trust, scope, and access control once tool exposure becomes a standardized, easily-scaled capability rather than a one-off integration.
