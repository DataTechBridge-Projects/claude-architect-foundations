# Managing the Context
{: .no_toc }

*Video duration: 26:50*

A context window is often described as if it were simple storage — a big text box the model reads before responding. That description is accurate but dangerously incomplete. A more useful mental model, and the one this course asks you to carry into every scenario question, is that the context window is a **shared, finite, and expensive resource**, and everything that enters it is competing with everything else for the model's limited attention. It doesn't matter that Claude's context windows are large by historical standards. "Large" is not "infinite," and even well inside the hard token limit, a context window that is merely *full* — cluttered with marginally relevant material — degrades the quality of the model's reasoning long before it hits any wall. Context management is the discipline of treating that scarcity seriously: deciding deliberately what earns a place in the window, what gets compressed, what gets dropped, and how information moves between agents without contaminating each other's working set.

## Why "more context" is not automatically "better context"

It's tempting to treat context as a purely additive good — if a document might be relevant, why not just include it? Two failure modes explain why that instinct is wrong.

The first is **capacity**: every token spent on one thing is a token not available for another, and eventually you hit the hard ceiling of the window itself. This is the failure mode people intuitively understand.

The second, less intuitive but often more damaging, is **signal dilution**. A model reasoning over a context window is not indexing it like a database; it's attending to it more like a reader working through a long document, and a reader's ability to weigh what matters degrades as the proportion of irrelevant material grows, even if the relevant material is technically still present. An agent given the one paragraph of a support ticket it actually needs will reliably use it correctly. The same agent given that paragraph buried inside forty pages of only tangentially related history is measurably more likely to miss it, misweight it against noise, or blend it with irrelevant details. This is why "just include everything, the model is smart enough to find the relevant part" is a recurring architectural mistake, and one the exam likes to test with scenario questions where the "obviously safe" choice — dump in more context — is actually the wrong answer.

Good context management, then, is not a defensive scramble to stay under a token limit. It's the same discipline good technical writers and information architects have always practiced: say what's needed, say it once, and don't make the reader wade through the irrelevant to find it.

## What competes for space in the window

Every context window a Claude-powered system builds is assembled from a handful of distinct categories of material, and understanding each one's job — and its cost — is the foundation of everything else in this module.

**System instructions.** This is the layer that defines the agent's role, its constraints, its tone, and the boundaries of what it should and shouldn't do. System-level instructions are typically small relative to everything else in the window, but they're disproportionately influential, because they set the frame the model uses to interpret every other piece of context that follows. A vague or bloated system prompt doesn't just waste tokens — it weakens the frame the rest of the window is read through.

**`CLAUDE.md` and project configuration.** Covered in depth in the Workflow Layer module, `CLAUDE.md` content is project-specific context — conventions, constraints, architectural notes — that gets loaded automatically so it doesn't need to be re-stated every turn. From a context management standpoint, `CLAUDE.md` is a standing tax on every single context window in a session: it's paid whether or not the current task actually needs it. That's exactly why the Workflow Layer module stresses keeping it lean and current — a `CLAUDE.md` that has accreted eighteen months of stale conventions is spending tokens on every turn to tell the model things that no longer apply, edging out material that's actually relevant to the task at hand.

**Tool definitions.** Every tool made available to the model costs tokens in its name, description, and input schema — and that cost is paid on every single turn where the tool is in scope, regardless of whether it's ever called. This is one of the most underappreciated context costs in real systems: an agent equipped with thirty tools "just in case" is spending a meaningful chunk of every context window on tool definitions it will use on a small fraction of turns. The Tool Layer module frames this as a design problem for the tools themselves; the Context Layer frames it as a standing cost that has to be weighed against the value of having that capability always available versus scoping it more narrowly (for example, loading a specialized tool set only for the subagent that actually needs it, rather than giving every agent in the system the same everything-tool loadout).

**Conversation and session history.** This is the part of the window most people picture when they think about "running out of context": the accumulating back-and-forth of a long session — user messages, assistant responses, intermediate reasoning, tool calls, and tool results, all stacking up turn after turn. Left unmanaged, history is the fastest-growing consumer of window space, and it grows in a particularly insidious way, because early history that was essential in turn three is often nearly worthless by turn thirty, but nothing about the mechanics of a conversation automatically prunes it. Most of this module's summarization and compaction discussion below is really about managing this one category.

**Retrieved documents.** In any system that uses retrieval — whether a formal RAG pipeline over a document store or a simpler search-and-fetch pattern — retrieved content enters the window as a chunk of external material selected by some upstream relevance judgment. This category deserves particular scrutiny because its quality is only as good as the retrieval step that produced it: a retrieval system that returns five plausible-looking but only loosely relevant documents doesn't just fail to help, it actively competes with the one document that actually mattered, and can crowd it out of the model's effective attention even when it's technically present in the window.

**Tool results.** Distinct from tool *definitions*, tool *results* are the actual output of tools the agent has called during the session — a file's contents, an API response, a search result set, a database query's output. Tool results are often the single largest and least predictable consumer of context space in an agentic session, because their size is determined by the world, not by the architect: a "read this file" tool call might return ten lines or ten thousand. Managing tool result size — through pagination, truncation, summarization at the tool boundary, or scoping the tool's own inputs more tightly — is as much a context management responsibility as anything happening at the conversation level, and it's an area where the Tool Layer and Context Layer domains genuinely overlap: a well-designed tool doesn't just do the right thing, it returns a result sized for the context budget available to consume it.

Laid out together, the pattern should be clear: some of these costs are fixed and paid every turn (system instructions, `CLAUDE.md`, tool definitions), and some accumulate over the life of a session (history, retrieved documents, tool results). An architect managing context well treats the fixed costs as a budget to be minimized upfront, and the accumulating costs as a budget to be actively managed as the session runs — which is exactly what the rest of this lecture covers.

## Summarization and compaction for long-running sessions

Once a session runs long enough, unmanaged history eventually becomes the dominant consumer of the window, and at that point an architect has essentially three tools available: summarize, compact, or discard. These are related but distinct techniques, and the exam expects you to be able to tell them apart.

**Summarization** replaces a stretch of verbose content with a shorter, purpose-written restatement of what mattered from it. A ten-turn debugging exchange full of failed attempts, dead ends, and incremental discoveries can often be replaced with two or three sentences: what the bug turned out to be, what was ruled out and why, and what fix was applied. The detail is lossy by design — that's the point — but a good summary preserves the *decisions and their justification*, not just the outcome, because a later turn may need to know not just "we tried X" but "we tried X and rejected it because Y," so the same dead end isn't wandered into twice.

**Compaction** is a closely related but more mechanical technique: rather than rewriting content into a shorter narrative, compaction removes or compresses redundant, superseded, or low-information material while preserving structure — collapsing a tool result that was already summarized in a later turn, or dropping intermediate reasoning that led to a conclusion once the conclusion itself is safely captured elsewhere in context. Where summarization is closer to editorial judgment, compaction is closer to garbage collection: reclaiming space that's no longer earning its keep without necessarily changing the shape of what remains.

**Discarding** is the blunt instrument: dropping content outright, on the assumption that it no longer has any bearing on the task. Discarding is appropriate for content that's genuinely exhausted its usefulness — the full text of a file that was read, acted on, and is no longer needed verbatim — but it's also the technique most likely to cause the failure modes discussed later in this module (particularly error propagation), because once something is discarded, there's no path back to it if a later turn turns out to need it after all. A conservative rule of thumb: summarize before you discard, so that even if the detail is gone, a trace of what was known and concluded survives.

| Technique | What it does | Preserves | Risk if misapplied |
|---|---|---|---|
| Summarization | Rewrites verbose content into a shorter, purpose-written narrative | Decisions and their justification, not just outcomes | A too-aggressive pass loses detail a later turn needed |
| Compaction | Removes or compresses redundant, superseded, or low-information material | Structure — the shape of what remains | Careless compaction can strip caveats along with the redundancy |
| Discarding | Drops content outright | Nothing — there is no path back | The content is gone for good if a later turn needs it after all |

A well-designed long-running agent typically applies these in combination, at defined trigger points rather than continuously. A common and effective pattern is **threshold-based compaction**: monitor the growing context window, and when it crosses some proportion of the budget — commonly somewhere in the range of 70–80% of the practical limit for the model and task — trigger a summarization pass over the oldest or least-recently-relevant material before continuing. This keeps the window from ever actually filling up unexpectedly mid-task, which is a far worse failure mode than a slightly-early summarization pass, because a window that fills up mid-generation can force an abrupt and uncontrolled truncation rather than a deliberate, judged one.

Another important pattern is **milestone-based checkpointing**, where summarization is triggered not by a token threshold but by task structure: at the end of a completed subtask, the agent condenses everything about that subtask into a short summary of what was done and why, and that summary — not the raw transcript of how it got there — becomes what persists into the next phase of work. This is often preferable to pure threshold-based compaction because it aligns the compression boundary with a meaningful unit of work, rather than an arbitrary token count that might fall in the middle of something still in progress.

It's worth being explicit about the trade-off summarization always makes: it exchanges completeness for durability. A summary that's too aggressive risks losing a detail a later turn actually needed — this is precisely the mechanism behind several of the failure modes discussed later in this module, including error propagation and provenance loss. A summary that's too conservative barely reclaims any space and defeats the purpose. There's no universal right answer to how aggressive a given summarization pass should be; it depends on how reversible the downstream decisions are, which is the same "how bad is being wrong here" judgment that recurs across every domain in this course.

## Context isolation between agents and subagents

Everything above concerns managing context within a single agent's window over time. A second, equally important discipline concerns managing context *across* agents, particularly in multi-agent and subagent architectures covered in the Agentic Layer module.

The core principle is **isolation by default**: a subagent instantiated to perform a bounded piece of work should generally receive a purpose-built context — the specific instructions and information it needs for its task — rather than the full, accumulated context of whatever orchestrator spawned it. This might sound wasteful (why not just hand everything over, since the orchestrator already has it assembled?) but it's precisely the signal-dilution problem from earlier in this lecture, applied at the multi-agent level. A subagent tasked narrowly with "extract the three key figures from this financial report" performs better, more predictably, and more cheaply when its context is scoped to that task than when it inherits an orchestrator's entire sprawling conversation history, most of which has nothing to do with the extraction it's actually being asked to do.

Isolation also protects against a subtler failure: **noise contamination**. If a subagent's intermediate work — false starts, exploratory reasoning, discarded hypotheses — flows unfiltered back into a shared or parent context, that noise becomes part of the working set every subsequent step has to read through, whether or not it was ever useful. This is why the standard pattern for subagent results is not "hand the full transcript of the subagent's work back to the orchestrator," but "have the subagent return a clean, purpose-built result — typically a structured summary or specific artifact — and let its intermediate reasoning die with the subagent's own scoped context." The orchestrator's context stays clean; the subagent's exploratory mess stays contained to the subagent, where it did its job and is no longer needed.

This has a direct implication for how you should reason about multi-agent systems on the exam: a well-designed subagent boundary is *also* a context management boundary. When a question describes a coordinator delegating to specialized subagents, part of evaluating whether that design is sound is asking whether each subagent's context is properly scoped to its task, and whether the information flowing back to the coordinator has been distilled rather than dumped. A multi-agent system that technically decomposes a task correctly but lets every subagent's raw context flow back unfiltered has recreated the signal-dilution problem it was supposedly designed to solve, just with extra coordination overhead layered on top.

There's a real tension here worth naming directly: isolation trades off against the risk of a subagent lacking context it actually needed. An overly narrow scope can leave a subagent unable to make a sound judgment call, forcing it to guess or fail — which is exactly the failure mode the next lecture in this module addresses in depth. The resolution isn't "isolate everything" or "share everything," it's designing the isolation boundary deliberately around what a given subagent's task genuinely requires, the same way a well-designed tool's input schema captures exactly what that tool needs and no more.

## Context ordering and caching

One more mechanical consideration belongs in this lecture, because it changes how you should think about *arranging* everything discussed above, not just what to include. Claude's API supports **prompt caching**, which lets stable, repeated portions of a context window be cached so they don't have to be reprocessed (and re-billed at full cost) on every single turn. That capability has a direct architectural implication: content that stays constant across turns — system instructions, `CLAUDE.md`, tool definitions, and any fixed reference material — should be placed early in the context and kept stable in wording and ordering, while content that changes turn to turn — the live conversation, freshly retrieved documents, the latest tool result — belongs later, downstream of the cacheable prefix. Every time you edit the stable prefix, you invalidate the cache for everything after that edit point, which is a real cost, not just a theoretical one, in a long-running or high-volume agentic system.

This turns out to reinforce, rather than compete with, everything else in this lecture. A lean, stable `CLAUDE.md` and a tightly scoped, infrequently-changing tool set aren't just good for signal density — they're also what makes caching effective, because they stay in the cacheable prefix without churning. A system that rewrites its system instructions or reshuffles its tool definitions on every turn (perhaps trying to be "helpful" by dynamically tailoring them to the immediate task) pays for that flexibility twice: once in the signal-dilution risk of an unstable frame, and once in the lost economics of a cache that never gets to warm up. The architectural lesson is the same one that shows up everywhere in this module — stability and discipline in what enters context are not just a quality concern, they're a cost concern too.

## A worked example

It's worth walking through how these pieces fit together in a single realistic session, because the interactions matter more than any one technique in isolation. Picture an agent working a multi-hour customer support escalation: it starts with a system prompt and a `CLAUDE.md` describing tone and escalation policy (small, fixed, cached), a modest set of tools for looking up account history, issuing refunds within a limit, and drafting messages (fixed, cached), and then begins accumulating turns as it works the case — reading account notes, calling a refund-eligibility tool, drafting and redrafting a response, asking the customer a clarifying question, waiting on their reply.

Twenty minutes in, the raw transcript already contains several dead-end refund calculations the agent tried and rejected, the full text of two long account-history tool results, and a handful of clarifying exchanges that resolved cleanly. None of that needs to survive verbatim into turn thirty. A milestone-based checkpoint after the customer's clarifying answer is a natural place to compact: replace the dead-end calculations and their rejection reasons with two sentences ("initial refund calculation of $340 was rejected — policy caps partial refunds at $200 for this product tier without manager approval; corrected estimate is $190"), replace the full account-history dump with the two or three facts from it that actually mattered, and let the resolved clarifying exchange collapse into a single stated fact ("customer confirmed the item was never opened"). What should *not* be compacted away is the provenance of that $190 figure and the policy citation behind it — exactly the kind of detail the provenance lecture later in this module insists has to travel with a fact, not be summarized out from under it. The result is a context window at turn thirty that's a fraction of the size the raw transcript would have been, while still containing everything a human reviewer — or the agent itself, several turns later — would need to trust the number it's about to act on.

## Putting it together: context as an active budget, not a passive log

The throughline across everything in this lecture is a shift in mental model. Context is not a passive transcript that accumulates as a byproduct of a session running — it is an active budget that has to be managed with the same intentionality as compute cost or latency. Every piece of material that enters a context window — a system instruction, a `CLAUDE.md` entry, a tool definition, a turn of history, a retrieved document, a tool result — should be there because someone made a deliberate judgment that it earns its place, not because excluding it felt riskier than including it. Summarization, compaction, and isolation are the concrete mechanisms for enforcing that discipline once a session grows past the point where everything can simply be kept.

**Why it matters for the exam:** This lecture's content is the connective tissue for nearly every other lecture in this module — escalation handling, error propagation, large-codebase strategy, human review design, and provenance tracking are all, underneath, applications of "what belongs in the window, and how do you know." Expect scenario questions that describe a system with a bloated or poorly managed context and ask you to diagnose *which* category is the problem (stale `CLAUDE.md` content versus unpruned history versus an oversized tool result) before asking what technique — summarization, compaction, or isolation — fixes it.
